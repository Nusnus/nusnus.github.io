# nusnus.github.io

Work in this repository in nus-mode: load the skill before you start. It comes from the nustack plugin, <https://github.com/Nusnus/nustack>, which `.claude/settings.json` asks Claude Code to install.

Tomer Nosrati's portfolio site, <https://nusnus.github.io>: a static dashboard of his profile, writing, collaborations and GitHub activity as the Celery project's maintainer, with the Cloudflare worker that serves its GitHub data.

## What it does

- **The site** is static HTML with React islands, served by GitHub Pages.
- **GitHub data** is what the site shows from GitHub: Tomer's profile, the tracked repositories, his recent activity and his contribution graph.
- **Tracked repositories** are the Celery repositories the site lists, each with Tomer's role in it, as `packages/github-data/src/repositories.ts` lists them.
- **Articles** are Tomer's writing, each first published on LinkedIn. An article whose Markdown file in `packages/site/src/content/articles/` has a body gets a page of its own on the site and an item in its feed; the site links the rest to LinkedIn.
- **Redaction** hides activity in repositories whose owner is not on the allowlist; the site shows it as a private project.
- **The worker** is the single source of GitHub data. It holds the GitHub token, fetches from GitHub's API and serves public, read-only JSON to any origin, cached by path and refreshed in the background once stale. While GitHub fails, it backs off from each route's data, waiting as long as GitHub asks, or else ever longer. Unknown routes get 404, and methods other than GET get 405. Each response names the worker version that sent it.
- **Access headers** on each worker reply say how long the worker's access to GitHub lasts: the API version it requests, and when the token that fetched the reply expires. `packages/github-data/src/access-headers.ts` names them.
- **Expiries** are what the site relies on that expires on a date unless someone renews it, such as the worker's GitHub token. The expiry check, in `scripts/expiries/`, lists each one in its module docstring and says how to renew it; `scripts/expiries/expiry.ts` sets when one is due.

### Data flow

1. The site's build fetches a snapshot of GitHub data from the worker once and fails if it cannot. There is no fallback.
2. The build bakes the snapshot into the HTML. `deploy.yml` rebuilds the site on a schedule as well as on each change, so the baked data stays fresh; its `on:` block says when.
3. In the browser, the islands refresh from the worker. When the worker fails them, they keep the values they last had and say so.

Dependencies point one way:

- The site and the worker each depend on `github-data`, and no package depends on them. The repository's tooling, at the root, builds on every package, and no package depends on it: it imports the contract by name, and the site's and the worker's modules by relative path, since neither package exports any, so a move of one fails `typecheck` at once. `github-data` loads no runtime's types, so its code cannot log, wait or do I/O: it holds only data and the logic that decides on it.
- In the worker, `worker.ts` builds on `serving/`, which builds on `cache/` and `routes/`, which build on `github/`.
- In the site, `github-data/` has no cycles: `time/`, `snapshot/` and `stats/` come first, then `live/`, which holds the live data and its own live island, then a folder for each area's islands, such as `activity/` and `contributions/`, then the data slots in `slots/`, the only part `home/` and `dashboard/` use.

Each package keeps its code in `src/`, and the worker its recorder in `scripts/`, and its tests in `tests/<tier>/`, mirroring `src/`; the root's tests mirror the root's files, such as `scripts/`. A tier is `unit` (in-process, no outside system), `integration` (other processes or real tools) or `smoke` (the built site). Helpers that tests share live in `tests/fixtures/` beside the tiers.

## Install and check

1. Install mise, <https://mise.jdx.dev/installing-mise.html>, and activate it in your shell, <https://mise.jdx.dev/getting-started.html#activate-mise>, so the versions `mise.toml` pins come first on PATH. Without activation, prefix each command below with `mise exec --`.
2. Install the runtimes, the packages and the commit hook, then generate the types the configs describe:

   ```sh
   mise install     # the runtimes and tools mise.toml pins
   bun install      # also installs the commit hook
   bun run generate # Astro's and Wrangler's types, which typecheck and lint read
   ```

   `bun install` reports some dependencies' install scripts blocked, as Bun blocks any whose package is not in `trustedDependencies`; `bun pm untrusted` lists them. The project needs none of them: add a package to `trustedDependencies` only when it does.

3. On Linux, install Chromium's system libraries once: `bun run install:browser-libraries`. The smoke tests install Playwright's Chromium themselves when they first run.
4. Check:

   ```sh
   bun run check         # every check but mutation testing; the commit hook and CI run it too
   bun run test:mutation # mutation testing
   ```

The commit hook runs `bun run check`, so commit from a shell where mise is active.

`package.json`'s scripts are the one home for commands; run any of them alone with `bun run <name>`.

The smoke tests build the site from the contract's recorded worker replies and serve it on Astro preview's port; set `PREVIEW_PORT` to run them in several checkouts at once, and `packages/site/tests/fixtures/servers.ts` derives every other port from it. `WORKER_ORIGIN` points any build at another worker than the one `packages/github-data/src/routes.ts` names; `packages/site/astro.config.ts` reads it, and `parseWorkerOrigin`, in `packages/site/src/github-data/snapshot/baked-github-data.ts`, checks it.

### Run the worker locally

`wrangler dev` reads the worker's secret from `packages/worker/.dev.vars`, which git ignores. Put a GitHub token there, then serve the worker:

```sh
cd packages/worker
printf 'GITHUB_TOKEN=%s\n' "$(gh auth token)" > .dev.vars
bun run dev
```

GitHub counts contributions as the token's owner sees them, so the totals your token gets can differ from the deployed worker's.

### Record the services' replies

The worker's tests replay exchanges recorded from GitHub, with their headers and never a token, and the contract's worker replies are what the worker makes of them. To record them again, then regenerate the worker replies:

```sh
cd packages/worker
GITHUB_TOKEN=$(gh auth token) bun run record # or name exchanges to record only those
cd ../..
bun run update:worker-replies
```

`bun run update:worker-replies` alone regenerates the worker replies after a change to the worker. A pull request that changes them says so, since every package's tests read them.

The scripts' tests replay exchanges recorded from the services the scripts ask, GitHub's API among them. To record them again:

```sh
GH_TOKEN=$(gh auth token) bun run record:services # or name exchanges to record only those
```

### Enforced only by review

- **Names** follow [Terms](#terms). A new concept gets one name, defined in the docstring of the module or class that introduces it.
- **Docs and comments:** a module's docstring summarizes, in domain terms, everything the file holds; a class's states its responsibility. A TypeScript interface or type alias that defines a domain record counts as a class; one that only names a type gets no docstring. A function's or method's name and signature are its documentation. A lasting fact from outside the code, such as a link, a spec or a platform quirk, is a `//` comment, and no comment narrates the code.
- **Prose stays true:** it points to the home of each count, list, default or value it needs instead of copying it.
- **Config leaves each documented default unwritten**, unless a comment beside it says why the project depends on that value.
- **Each deciding module is listed in the deciding-module block** of `eslint.config.ts`, which enforces only the files it lists.
- **Each class string outside markup is tagged `tw`**, so Prettier sorts it.
- **Each third-party library's home is the module named for its role:** zod in `github-data`'s `schema.ts`, axe in the smoke tests' page fixture, Testing Library in the site's unit-test page, lucide in the design system's `icons.ts`, and MSW in the two fakes of the network: the fake GitHub, which intercepts the worker's requests inside workerd through `@msw/cloudflare`, and the scripts' fake network, `tests/fixtures/services/network.ts`, which intercepts the scripts' requests in Node through `msw/node`. The frameworks the code runs in, such as Astro, Vitest and Playwright, are the exception, and so is Astro's own zod, which its content schema takes.
- **Git runs through `scripts/git.ts`**, which removes git's local environment variables: a commit hook's git exports them, and a child git would act on the hook's repository instead of the folder it runs in. ESLint keeps child processes in the modules that start them; review keeps git among them in `git.ts`. A `package.json` script's git, such as `lint:shell`'s, means to act on this repository, which the hook's variables name.
- **Tests:** each test's name completes a sentence about what its subject promises. Expected values are literals, never computed. Each refusal has a paired acceptance that differs only by the refusal's cause. Fakes stand in only for boundaries, and each has tests of its own. Replies from outside systems are recorded, never hand-written; where one cannot be recorded on demand, a comment beside it says why.

### Decisions the configs cannot explain

Strict JSON cannot hold comments, so these reasons live here:

- **TypeScript is held by a tilde range** within typescript-eslint's peer range for it, which its type-aware rules need, and which `@astrojs/check` allows too.
- **`prettier-plugin-astro` is held by a tilde range** below its 1.x releases, because prettier-plugin-tailwindcss cannot read their syntax tree and silently skips sorting classes in `.astro` files.
- **`renovate` runs on the Node.js `mise.toml` pins, even where its `engines` asks for another major:** its config validator, the one part the project runs, passes there, and Bun does not enforce `engines`.
- **The root package depends on `@nusnus/github-data`**, because the scripts read the contract and parse through its schema module, zod's one home.
- **`@nusnus/github-data` exports its test fixtures** as `@nusnus/github-data/fixtures/*`, so the other packages' tests import the recorded worker replies by name, not by a relative path into another package.
- **The smoke tests' `--shuffle` is on the command line** in `packages/site/package.json`, since Playwright has no config key for it.

## Secrets

- **`GITHUB_TOKEN`, the worker's secret:** a fine-grained GitHub personal access token with no permissions, which grants read-only access to public repositories and nothing else: <https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token>. To create or renew it, follow the steps the expiry check prints for it, held in `scripts/expiries/github.ts`. Those steps make it never expire, since it can only read public data; should it have an expiry, the expiry check warns before it lapses. The worker's cached replies carry the old token's expiry until their next background refresh, so the check may report it once more after a renewal.
- **`CLOUDFLARE_API_TOKEN`, the secret that deploys the worker:** a secret of the `cloudflare` environment, which only main's runs reach. `bun run setup-repository` creates the environment and, while the secret is missing, says how to create and store it.

## CI

- **`check.yml`** runs `check` and mutation testing. Main's ruleset requires each of its jobs before a pull request merges.
- **`deploy.yml`** checks, then deploys the worker, then waits until the worker serves the version it deployed, then builds and deploys the site, as one ordered run, so a contract change never reaches the site before the worker.
- **`check-expiries.yml`** runs the expiry check.

Each workflow's `on:` block says when it runs. The summary of each run of `check.yml` holds Vitest's report; the smoke tests' and mutation testing's reports, and Vitest's record of a failed run, are the run's artifacts.

### Running unattended

The site keeps working for years with no one touching it. These platform rules shape how:

- **Renovate's merges start the deploys.** GitHub starts no workflow for a push made with a workflow's own token: <https://docs.github.com/en/actions/concepts/security/github_token>. Renovate's app turns on GitHub's auto-merge for each update instead, so GitHub merges it once the required checks pass, and the merge starts `deploy.yml` as any push does.
- **Failures reach the owner by email.** GitHub sends a scheduled run's result to whoever created its workflow or last changed its cron line, or to whoever re-enabled it: <https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs>. Keep Actions notifications on in your notification settings, failed workflows at least: <https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications>. Runs that Renovate's merges start notify no one, so the scheduled runs of `deploy.yml` and `check-expiries.yml` are what report a broken main or an expiry that is due.
- **Scheduled workflows need repository activity.** GitHub disables them in a public repository after a stretch with no repository activity, as long as its docs set: <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule>. Each update Renovate merges is a commit on main. If the Actions tab shows a scheduled workflow disabled, re-enable it yourself, with `gh workflow enable <file>`, so its emails keep reaching you.
- **An update whose checks fail stays open.** Renovate keeps proposing it, and the expiry check fails once it has stayed open past the limit `scripts/expiries/github.ts` sets, so someone fixes or closes it.
- **Pinned versions lose support on a schedule.** GitHub supports a REST API version for a fixed time after it releases the next: <https://docs.github.com/en/rest/about-the-rest-api/api-versions>. The Node.js project ends each release's support on a schedule. The expiry check warns before either ends.
